# ② 팟 개설·참여·실시간 정산 갱신 (핵심 기능)

담당: 최지원(백엔드, 리드) + 도우현(프론트) · 관련 화면: [S4~S8](../DESIGN_HANDOFF.md)

## 왜 필요한가 (근거)

대용량-소포장 단가 격차가 품목별 30~53%에 달해 절감 여지가 크지만, 기존 당근마켓·오픈채팅 공동구매는 반경이 넓어 이동 피로가 크고, 대표가 정산·회수를 전담하다 이탈하면 전체가 중단되는 구조적 취약점이 있었다. 소분소분은 건물 단위로 반경을 좁히고, 대표 수고비를 정산식에 정률로 내장해 대표가 손해 보지 않게 설계한다.

## 사용자 시나리오

**팟 생성 (대표)**
1. 건물 홈에서 "+ 팟 만들기"를 누른다.
2. 상품명, 목표 총액(또는 목표 인원), 대표 수고비율(기본 5%), 마감 기한을 입력한다.
3. 팟이 생성되고 건물 홈 리스트에 노출된다.

**팟 참여 (참여자)**
1. 팟 상세 화면에서 실시간 1인당 예상 금액을 확인한다.
2. "참여" 버튼을 눌러 참여를 확정한다.
3. 서버가 참여자 수 증가를 반영해 1인당 금액을 재계산하고, WebSocket으로 팟을 보고 있는 모든 사용자에게 갱신된 금액을 브로드캐스트한다.

**팟 마감 (대표)**
1. 목표 인원/금액 달성 또는 마감 기한 도달 시 대표가 팟을 마감한다.
2. 마감 이후 신규 참여는 불가하며, 정산 단계(③)로 넘어간다.

## 비즈니스 규칙 — 금액 계산식

```
1인당 금액 = 총액 × (1 + 수고비율) / 참여자 수   (원 단위 올림, RoundingMode.CEILING)
```

- 참여자가 늘어날 때마다 이 식으로 재계산하고, 변경분을 즉시 브로드캐스트한다.
- 수고비율 기본값은 5%지만 대표가 팟 생성 시 조정 가능하게 할지는 팀 논의 (해커톤 데모에서는 고정값으로 단순화해도 무방).
- 마감 조건은 "목표 인원 도달" 또는 "마감 기한 도달" 중 대표가 선택 (MVP에서는 목표 인원 도달만으로 단순화 가능).

## 실시간 통신 규약

- 클라이언트는 `/ws-sobun` 엔드포인트로 STOMP 연결 후 `/topic/pods/{podId}`를 구독한다.
- 서버는 참여/탈퇴/금액 변경 시마다 `PodAmountUpdateEvent { podId, participantCount, perPersonAmount }`를 해당 토픽으로 발행한다.
- 연결이 끊겼다 재연결될 경우, 재연결 직후 REST `GET /pods/{id}`로 최신 상태를 한 번 동기화해야 한다(WebSocket은 놓친 이벤트를 재전송하지 않으므로).

## 엣지 케이스

- 동시에 여러 명이 "참여"를 눌러 목표 인원을 초과하는 경우(레이스 컨디션) → 서버에서 참여 처리를 원자적으로(트랜잭션/락) 처리해 초과 참여를 막아야 함.
- 참여했다가 취소하는 경우 → 취소 가능 여부와 그때 재계산 로직 필요 (마감 전까지만 취소 허용 권장).
- 대표가 팟을 마감하지 않고 잠수 타는 경우 → 마감 기한을 필수로 강제하거나, 일정 시간 지나면 자동 마감/자동 취소하는 정책 필요 (기존 서비스들의 실패 지점이었던 부분이므로 설계에서 명확히 할 것).
- 참여자가 0명인 채로 마감 시도 → 막아야 함.

## 열려있는 질문

- 목표 인원 vs 목표 금액 중 어떤 걸 기준으로 팟을 정의할지 (둘 다 지원하면 로직이 복잡해지니 MVP는 하나로 통일 추천).
- 대표 무응답 시 자동 마감/취소 정책을 해커톤 범위에 넣을지 여부.
