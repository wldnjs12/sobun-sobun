# 핸드오프 문서 (`docs/handoff/`)

기능별로 "지금까지 뭘 했고, 기획 대비 뭐가 다르고, 다음 사람이 뭘 알아야 하는지"를 남기는 곳입니다.

> ⚠️ 이 폴더의 문서들은 2026-10-03 기획 개편(QR→주소+GPS, 최저가 삭제, 커뮤니티 신설) **이전** 기록입니다. 각 파일 맨 위에 어떤 부분이 바뀌는지 머리말로 표시해뒀습니다. 최신 작업 분담은 [../REPLAN_WORK_ASSIGNMENT.md](../REPLAN_WORK_ASSIGNMENT.md) 참고.
`docs/features/*.md`(기획·설계)와는 목적이 다릅니다 — 저긴 "하기로 한 것", 여긴 "실제로 한 것과 그 차이"를 적습니다.

## 파일 규칙

- 파일명: `<기능-슬러그>.md` (예: `pod.md`, `auth.md`, `settlement.md`, `product.md`)
- 같은 기능을 여러 세션에 걸쳐 작업해도 **새로 만들지 말고 같은 파일을 갱신**합니다 (맨 위 "최종 갱신"만 바꾸고, 내용은 최신 상태로 덮어씀).
- 보통 `/handoff` 커맨드가 이 파일을 생성/갱신하고 커밋까지 합니다. 직접 써도 됩니다.

## 템플릿

```markdown
# 핸드오프: <번호> <기능명>

_최종 갱신: YYYY-MM-DD · 브랜치: feature/xxx_

## 이번 작업 요약
- 무엇을 구현/변경했는지

## 기획 대비 확인 (spec-check)
- 일치하는 부분
- 의도적으로 단순화한 부분 (이유 포함)
- 놓쳤거나 재확인 필요한 부분

## API 표면
- 구현된 엔드포인트 목록

## 알려진 제한사항 / TODO

## 다음 작업자 안내
- 로컬 실행/테스트 방법
- 다음에 할 일
```

## 관련 커맨드 (전체 루프)

1. `/plan <작업 설명>` — 관련 문서/코드를 먼저 읽고 Plan 모드로 구현 계획을 세움
2. (계획 승인 후 auto 모드로 구현)
3. `/spec-check [기능 키워드]` — 변경사항을 관련 기획 문서와 대조 (읽기 전용, 코드 수정 없음)
4. `/handoff [기능 키워드]` — 위 템플릿대로 문서를 쓰고 커밋
5. `/ship [기능 키워드]` — 3~4번(spec-check → 코드 커밋 → handoff)을 한 번에
6. `/pr` — push + PR 생성 (핸드오프 문서 없으면 훅이 막음)

## push 전 체크

`.claude/hooks/require-handoff-before-push.sh`가 `feature/*` 브랜치에서 `git push` 하기 전에
`docs/handoff/` 아래 파일이 이번 브랜치 커밋에 포함됐는지 확인합니다. 없으면 push를 막고 `/handoff` 실행을 안내합니다.
